# Critical Issues - Farm Direct AI Prototype

## P0: No Real Backend Authentication
- **Problem**: All authentication is client-side only via DemoContext localStorage. There is no real user registration, login, or session management. The role ('farmer' | 'consumer') is set locally and persisted to localStorage, but any user can switch roles by clearing storage or modifying the URL.
- **Why it matters**: A judge can easily pretend to be a farmer or consumer without any authentication. The system has no way to distinguish real users, track history, or enforce any per-user data. This fundamentally undermines the "direct farmer-to-buyer" concept which relies on trusted identities.
- **Exact file**: `src/context/DemoContext.tsx` lines 45-50 (localStorage role persistence); `src/pages/farmer/FarmerDashboardPage.tsx` line 43 (CURRENT_FARMER_ID = 'f-001'); `src/pages/consumer/ConsumerDashboardPage.tsx` no auth check
- **Recommended fix**: Implement real backend authentication (OAuth, JWT, or simple session-based auth). At minimum, add auth guards on API routes and prevent role-switching without proper login.

## P1: AI Backend Requires Undefined API Key
- **Problem**: The AI server (`server/aiIntentApi.mjs`) requires `AI_API_KEY` and `AI_API_MODEL` environment variables. The code has placeholder detection that defaults to `openai/gpt-4o-mini` via OpenRouter, but if the key is not configured, the API returns 503 with `fallback: true`. The frontend (`aiService.ts`) gracefully falls back to local parsing, but users are not informed that AI features are disabled.
- **Why it matters**: The project is marketed as "AI-powered" with voice intent extraction and assistant responses. If the AI key is not set, the system works but without any AI - it's all local rule-based parsing. A judge expecting AI functionality would find it disabled. The warning in the code ("AI_API_KEY was placeholder. Defaulting to openai/gpt-4o-mini") admits this is not a real integration.
- **Exact file**: `server/aiIntentApi.mjs` lines 30-38 (AI_API_MODEL placeholder detection); lines 40-46 (AI_API_KEY warning); `src/services/aiService.ts` lines 375-429 (parseVoiceIntent with fallback logic)
- **Recommended fix**: Either configure a valid OpenRouter API key in .env, or remove the AI dependency and clearly document that all "AI" features are local rule-based parsing.

## P1: All Data Is Mocked/Fake - No Real Database
- **Problem**: Every data point - farmers (f-001 through f-015), buyers (b-001 through b-010), produce listings, orders, logistics vehicles, storage units, FPOs, shipments - comes from static `mockData.ts` JSON or `produce-store.json`. There is no real database, no server-side data persistence beyond localStorage, and no data model beyond JSON files. The server `aiIntentApi.mjs` reads from and writes to `produce-store.json` on disk, but this is only for the produce-add feature, not the full system.
- **Why it matters**: A judge asking "Show me your database" or "How does data persist?" has no real answer. The system cannot survive a page refresh losing localStorage, cannot scale, and cannot support multiple users. The demo is fragile - clear browser data and the entire prototype vanishes.
- **Exact file**: `src/data/mockData.ts` (936 lines of hardcoded mock data); `server/data/produce-store.json` (file-based storage); `src/services/farmerInventoryService.ts` lines 57-77 (localStorage getStored/setStored)
- **Recommended fix**: Either connect to a real database (PostgreSQL, MongoDB, Firestore) or clearly document this as a prototype with in-memory/mock data only.

## P1: Matching Is Rule-Based, Not AI-Based
- **Problem**: The matching engine in `aiService.ts` uses hardcoded weighted scoring: availability (30%) + price (25%) + distance (20%) + quality (15%) + reliability (10%). This is explicitly rule-based algorithmic matching, not machine learning or LLM-based matching. The `matchFarmers()` and `matchBuyers()` functions filter by product name match then compute scores using the `weightedScore()` function - there is no AI/ML model involved beyond the voice intent parsing LLM.
- **Why it matters**: The project is positioned as having "AI matching" between farmers and buyers. A judge testing the matching would find pure rule-based scoring. If they change quantity or location, the scores change predictably based on the formula, not based on any learned model. The `confidence` field in match scores (e.g., 0.98) is derived from the score, not from any model confidence.
- **Exact file**: `src/services/aiService.ts` lines 562-587 (matchFarmers); lines 589-614 (matchBuyers); lines 193-200 (weightedScore); lines 179-189 (priceScoreForBuyer/seller); lines 191 (distanceScore)
- **Recommended fix**: Either integrate a real AI/ML matching model, or honestly document that matching is rule-based with configurable weights - and add a note that real AI matching would require a trained model.

## P1: No Real Order Creation or Management
- **Problem**: Orders are created via the `createOrder()` helper function in `mockData.ts` and stored in `mockOrders` array + `activeOrder` in DemoContext. There is no backend API for creating orders from the frontend. The order flow is: farmer lists produce → buyer views marketplace → buyer connects → simulated call → order created manually via mock data. The `activeOrder` is initialized to `mockDefaultActiveOrder` and never genuinely created through a business transaction.
- **Why it matters**: A judge asking "Place an order" or "Show me the order creation flow" will find the order is just a pre-existing mock state, not something created through the system. There's no payment, no escrow, no agreed price negotiation flow - the price is just set by the matching algorithm. The "Direct P2P Connection" simulation in `ConsumerCallPage.tsx` uses timed timers (1.5s to active, 5.5s to negotiated) rather than any real business logic.
- **Exact file**: `src/data/mockData.ts` lines 841-903 (createOrder function + mockOrders array); `src/context/DemoContext.tsx` lines 805-839 (mockDefaultActiveOrder); `src/pages/consumer/ConsumerCallPage.tsx` lines 15-25 (timed call status transitions)
- **Recommended fix**: Build a real order creation API endpoint that takes matched farmer/buyer/produce details, stores the order in the database, and sets up escrow/payment state.

## P2: No Real Logistics or Fulfillment Integration
- **Problem**: Transport, delivery tracking, GPS, and cold storage are all UI simulations with mock data. `mockLogisticsVehicles` (10 vehicles) are static. Vehicle selection in `ConsumerLogisticsPage` merely updates `activeOrder.logisticsAllocated` local state. `RouteCard` displays hardcoded route data from `mockData.ts` (consumerTomatoRoute, farmerPotatoRoute). Cold storage selection in `ConsumerStoragePage` similarly just updates `activeOrder.storageAllocated`. There is no transport API, no dispatch logic, no GPS coordinates, no real ETA calculation, and no cold storage booking backend.
- **Why it matters**: The farmer-to-buyer flow promises "fulfilment coordination" but has no real fulfilment engine. A judge asking "Track the delivery" or "Show me the cold storage allocation" will see only UI state changes, not real backend processes. The GPS/ETA tracking in `ConsumerTrackingPage` displays simulated data (Suresh Verma EV Reefer, ETA 25 mins) with no real sensor data or route recalculation.
- **Exact file**: `src/data/mockData.ts` lines 670-681 (mockLogisticsVehicles); lines 685-704 (consumerTomatoRoute); lines 706-724 (farmerPotatoRoute); `src/pages/consumer/ConsumerStoragePage.tsx`; `src/pages/consumer/ConsumerLogisticsPage.tsx`; `src/pages/consumer/ConsumerTrackingPage.tsx`
- **Recommended fix**: Either integrate real logistics APIs (e.g., route optimization services, GPS tracking) or clearly document as a prototype with simulated logistics. At minimum, make the route data dynamic rather than hardcoded.

## P2: Voice AI Partially Functional - Browser STT + Optional LLM
- **Problem**: Browser SpeechRecognition works natively for speech-to-text. The voice pipeline in `VoiceAssistant.tsx` and `FarmDirectAssistantWidget.tsx` implements the full UI flow: start listening → onresult → processTranscript → parseVoiceIntent → generateAssistantResponse. However, the LLM step (`/api/voice-intent` and `/api/assistant-response`) requires `AI_API_KEY` in `.env`. Without it, the system falls back to `parseVoiceIntentFallback()` local parsing which is functional for common phrases but cannot handle arbitrary user input, complex Hindi constructions, or out-of-vocabulary terms. The user is not clearly informed when AI is vs. local fallback mode.
- **Why it matters**: A judge speaking Hindi or Hinglish may get different results depending on whether the AI key is configured. The frontend tries to be transparent (shows 5-phase lifecycle: listening → understanding → searching → responding → speaking), but the fallback to local parsing is not explicitly labeled as "not AI". The voice pipeline is the primary UI interaction method, and if the AI backend is down, the experience degrades significantly.
- **Exact file**: `src/components/VoiceAssistant/VoiceAssistant.tsx` (970 lines full voice pipeline); `src/components/Assistant/FarmDirectAssistantWidget.tsx` (full assistant drawer); `src/services/aiService.ts` lines 375-429 (parseVoiceIntent with fetch→fallback→validate); lines 441-496 (assistantResponseFallback)
- **Recommended fix**: Clearly surface AI status to users (e.g., "AI assistant available" / "Using local parsing"), or ensure the .env is configured for the demo, or redesign the voice pipeline to work completely offline with local parsing.

## P2: No Real Database - Data Lost on Clear/Browser Reset
- **Problem**: Related to P1, but specifically: all data stored in browser `localStorage` (farmer inventory via `farmerInventoryService`, active order via `storageService`, assistant widget state via `FarmDirectAssistantWidget`). If the user clears browser data, opens in incognito, or switches devices, all progress vanishes. The `produce-store.json` on the server disk is a separate file that persists across sessions but only for produce added via the API, not for buyers, orders, matches, etc.
- **Why it matters**: A judge spending 10-15 minutes with the demo, adding produce, making matches, allocating storage, and planning logistics - all of it disappears if they refresh, clear cache, or open on another device. The demo is not persistent. The `subscribe` pattern in `farmerInventoryService` (listening to `farmdirect:inventory-updated` event) only works within the same browser session.
- **Exact file**: `src/services/farmerInventoryService.ts` lines 57-77 (localStorage STORAGE_KEY); lines 221-229 (subscribe method); `src/services/storageService.ts` lines 4-5 (STORAGE_KEY localStorage); `src/context/DemoContext.tsx` lines 45-50 (localStorage role/lang persistence)
- **Recommended fix**: Either implement real server-side persistence (database) or clearly document the session-only limitation and provide a "export/import data" feature for demo purposes.

## P3: CORS and API Configuration Is Fragile
- **Problem**: The AI server (`server/aiIntentApi.mjs`) has `getAllowedOrigin()` that dynamically determines allowed CORS origins based on `AI_ALLOWED_ORIGIN` env var. If not set, it auto-detects localhost origins. The server starts on port 8787, the Vite frontend on 5173 (or 5176). The `.env.example` doesn't clearly document all required vars. The `runBoth.mspawn` script starts both, but if ports are conflicted, it can fail. The CORS configuration allows `*` by default if `AI_ALLOWED_ORIGIN` is empty or `'*'`.
- **Why it matters**: A judge running the demo locally might encounter CORS errors, port conflicts, or the AI server failing to start. The system assumes specific port configurations. The warning "If port 5173 is busy, Vite will auto-pick 5176 (allowed by CORS now)" indicates port management is a known pain point.
- **Exact file**: `server/aiIntentApi.mjs` lines 184-196 (getAllowedOrigin); lines 30 (PORT = AI_INT_PORT ?? 8787); `server/runBoth.mjs` lines 14-15 (spawn ai + vite); `package.json` scripts (dev, dev:ai, dev:all)
- **Recommended fix**: Document required .env variables clearly; make port configuration more flexible; add startup validation.

## P3: No Testing Infrastructure
- **Problem**: No unit tests, integration tests, or API test files found in the repository. The `aiService.ts` contains demo input arrays (`voiceIntentDemoInputs`, `assistantResponseTestCases`) and test runner functions (`runVoiceIntentDemoCalls()`, `runAssistantResponseTests()`), but these are development utility functions, not a test suite. No Jest, Vitest, or other test framework configuration is visible. The `package.json` only has `dev`, `build`, and `preview` scripts.
- **Why it matters**: A judge or reviewer cannot verify any feature with automated tests. Critical bugs in matching, AI parsing, or voice pipeline would go undetected. The demo relies on manual inspection and chance that the right inputs produce the right outputs.
- **Exact file**: `src/services/aiService.ts` lines 682-725 (voiceIntentDemoInputs, aiServiceDemoCalls); lines 727-792 (assistantResponseTestCases); lines 784-793 (runAssistantResponseTests); `package.json` (only dev/build/preview scripts)
- **Recommended fix**: Add a test framework (Vitest or Jest) and write tests for critical paths: voice intent parsing, matching algorithm, produce addition, order creation.

## P3: No Real Payment or Escrow Integration
- **Problem**: The order system has `paymentStatus` types (pending/escrowed/paid/failed/refunded) and displays "Escrow Protected" badges, but there is no real payment processing, no UPI integration, no escrow service, and no financial transaction logic. The `totalAmount` is calculated as `quantityKg * agreedPricePerKg` and displayed, but no money actually moves. The "Direct payout • UPI" claim in the UI is not backed by any integration.
- **Why it matters**: The disintermediation promise ("0% commission, direct payout") is not technically supported. A judge asking "How does the farmer get paid?" has no real answer beyond "it's simulated." The intermediary fee elimination (`impact.intermediaryFeeEliminated`) is a calculated number, not a real transaction.
- **Exact file**: `src/types.ts` lines 39 (PaymentStatus type); `src/data/mockData.ts` lines 814-819 (activeOrder impact with intermediaryFeeEliminated); `src/pages/farmer/FarmerOrderPage.tsx` lines 39-47 (payout summary with "Direct Bank Transfer on Delivery")
- **Recommended fix**: Either integrate a real payment gateway (UPI API, escrow service) or honestly document that payments are simulated for the prototype.

## P3: Inconsistent Data Modeling - farmerId vs fpoId vs fpoMember
- **Problem**: The data model has some inconsistencies. Farmer IDs are `f-001` through `f-015`, FPO IDs are `fpo-001` through `fpo-005`, and some farmers have `fpoMember: true` with `fpoId: 'fpo-001'` while others have `fpoMember: false` and no `fpoId`. The `mockFarmers` array in `server/aiIntentApi.mjs` has only 7 farmers with minimal fields compared to the 15 in `mockData.ts`. The `produce-store.json` backend has its own farmer mapping. The `Address` type has `formattedAddress` + separate `city`, `district`, `state`, `country` + `coordinates` but the address constructor in `mockData.ts` only sets `city`, `district`, `state`, `country`, `formattedAddress` - `coordinates` is always `undefined`.
- **Why it matters**: A judge inspecting the data model may find these inconsistencies. The `fpoId` vs `farmerId` vs `fpoMember` relationship is unclear in some places. The `coordinates` field being undefined despite being in the type definition suggests incomplete data modeling.
- **Exact file**: `src/types.ts` lines 41-56 (FPO type); lines 58-82 (Farmer type); `server/aiIntentApi.mjs` lines 91-98 (serverMockFarmers, only 7 farmers); `src/data/mockData.ts` lines 108-395 (mockFarmers, 15 farmers); lines 43-49 (address function - coordinates not set)
- **Recommended fix**: Clean up data model consistency; ensure all types are fully populated; document the FPO-farmer relationship.
